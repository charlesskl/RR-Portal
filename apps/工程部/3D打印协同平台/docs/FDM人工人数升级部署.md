# FDM 人工人数升级：管理员部署交接

本次允许产品和生产记录选择 **1、2、3 人**，默认3人。报价人工分摊按 `FDM每日人工费用 × 人数 / 3` 计算，之后沿用原耗时、机台分摊和利润公式。旧记录未保存人数时仍按3人计算；产品人数改变不批量改写历史记录。日报整日人工支出仍使用设置金额，人数不是整日出勤统计。

云端 `/authority` 的人数修改继续走“提交申请 → 现场执行并落盘 → 云端收到确认”的流程。产品仅修改人数时自动重算默认报价；同时明确提交报价则保留手填值。保留已有光固化记录的每克单价快照，不在此次升级中重新切换全局光固化价格。

## 部署对象与边界

- 仓库：`charlesskl/RR-Portal`，应用目录 `apps/工程部/3D打印协同平台`。
- 正式服务：根目录 `docker-compose.cloud.yml` 中的 **`printlink`**，数据卷 `printlink-data:/app/runtime`，端口3100。
- 保留现有 `.env.cloud.production`、账号、采集站令牌、机器映射、数据卷及统一记账绑定。
- 不运行应用子目录的独立 `compose.yaml` 创建第二套平台；不改门户、Nginx或其他服务。
- 不执行数据库回填、不清空库存、不重新启用统一记账。不随 PR 提交配置、业务数据、附件或凭据。

## 发布窗口与顺序

1. 管理员先审核 PR 和 CI。Windows 先运行下面的 `--check`；检查可在发布窗口前做，不写入文件。
2. 约定短暂停写窗口，暂停新增修改申请。停止 Windows 桥接和原3d-server及自动重启任务；按既有流程停机备份云端持久卷（两个数据库、附件与站点配置），另备份 Windows 两个完整目录。
3. 管理员按仓库既有 `/review-and-ship` / Actions 流程合并、构建和部署，仅更新 `printlink`。**本 PR 的提交者不代为合并或启动正式部署。**
4. Windows 可在同一停机窗口安装配套更新。云端就绪后，先启动原3d-server，最后启动桥接。
5. 两端刷新页面并等到确认时间晚于本次修改，再恢复业务。

PR等待审核期间，本地可继续使用旧版。不要本地先按1/2人正式报价并连接仍按旧规则计算的云端。已经先安装本地更新时，桥接保持暂停，直到两端配套完成。

## 云端管理员操作

遵循仓库部署流水线，不同时手工 SSH 重建同一服务，避免与 Actions 竞争。仅此应用源码变更应命中 `printlink` 的差异部署。不要执行全站 `docker compose up --build` 或 `down -v`。

备份沿用现有停机备份流程，包含 `/app/runtime/orders/printlink.sqlite`、`production.sqlite`、附件与 `stations.json`；只备份Git源码不够。保留回退用的上一镜像/提交以及最新账本和待处理申请状态。

部署后由管理员使用运维流程确认：

- `printlink` 容器健康；`node ops/healthcheck.mjs` 成功。
- `http://127.0.0.1:3100/api/health` 正常。
- 订单列表、附件上传/下载、账号搜索及原权限不变。
- `/authority` 的产品/记录编辑出现人数选择。
- 与现场完成下方端到端核对。

不必在云端运行增量更新器：正式 PR 已直接修改应用代码。`ops/update-fdm-pricing.cjs` 是现场增量安装工具；其 `cloud` 模式只供维护独立源码副本，不替代 RR-Portal 发布流程。

## Windows配套文件与命令

使用与本 PR 合并提交相同版本的现场更新包。若管理员从仓库重新打包，取以下文件并保留目录结构，放在**独立的升级包目录**（例如 `D:\PrintLink-PR1115`）。不要预先将包内 `shared` 等文件覆盖到现有桥接或原系统：更新器需要读取并备份目标目录的原文件，才能检查版本并保留已有修复。

- `ops/update-fdm-pricing.cjs`、`ops/restore-fdm-pricing.cjs`
- `legacy/pricing-patch.cjs`、`legacy/pricing-patch-rules.cjs`、`legacy/pricing-report-hashes.json`
- `shared/authority-commands.cjs`、`shared/production-report.js`、`shared/pricing-report.cjs`、`shared/pricing-records.cjs`

这些文件不覆盖 `collector`、现有 `business-sync-adapter.cjs`、`authority-durability.cjs`、异步写队列修复或站点配置。已有源代码形式的Node.js24+桥接支持直接运行。仓库的基础安装器另外补齐了新依赖文件，但**本次现场升级使用以下增量命令**，不改用旧安装器覆盖队列修复。

以下示例使用独立升级包 `D:\PrintLink-PR1115`，目标仍是已有桥接 `D:\PrintLinkBridge` 和原系统 `D:\3d-server`；替换为实际路径。不要从升级包启动桥接，不创建第二套业务目录：

```powershell
node "D:\PrintLink-PR1115\ops\update-fdm-pricing.cjs" windows "D:\PrintLinkBridge" "D:\3d-server" --check
# 停止桥接和原服务，完成两个目录的完整备份后：
node "D:\PrintLink-PR1115\ops\update-fdm-pricing.cjs" windows "D:\PrintLinkBridge" "D:\3d-server"
```

预检查会先校验所有修改点；版本不匹配时不写入文件。若缺少原有桥接接口，可能是先前整包替换 `server.js` 导致：保持停机，请使用现场已有的异步写队列兼容修复版安装器恢复接口，再重新检查；不要跳过检查或覆盖整份程序。

增量工具保留 `saveData(data, authorityWrite=false)`、现有回执校验及文件写队列。各目标目录生成 `.fdm-pricing-backup-*` 和恢复清单。重复运行无变更时不再改写文件。

**不要在此后用旧的整文件 FDM 更新包覆盖 `server.js` / `index.html`。**本次增量工具已经包含人数页面和字段更新。配置与业务数据均不由更新器修改。

## 验收用例

以独立测试产品验收，不直接改真实历史订单：PLA 32元/kg，60g，2.5h，数量1，机器21，FDM每日人工750元、每机日电费1.5元、损耗1.2、利润40%。

| 人数 | 预期产品报价 |
| --- | --- |
| 3 | 14.60元 |
| 2 | 10.95元 |
| 1 | 7.31元 |

1. 云端仅修改测试产品人数为1，提交原因；确认前不应提前记账。现场确认后，产品人数1、默认报价7.31，两端一致。
2. 新生产记录带入该产品人数；既有记录的人数不被产品改动覆盖。单独修改一条记录人数，应反映在该记录报价和对应日报/导出中。
3. 日报的整日人工仍为设置金额750元；材料、电费公式不随人数改变。
4. 同日期本地明细、日报、导出与云端一致，确认时间应晚于本次修改。超过90秒的延迟提示不算验收成功。
5. 抽查光固化旧0.8、新0.5记录，之后改变默认价不应改写历史金额。
6. 检查订单、附件、库存、采集站和机台映射未受升级影响；断网重试不应重复执行申请。

## 失败与回退

- 预检查失败：无文件写入；保留完整输出，停止升级。
- 程序写入失败：工具尝试恢复已写入文件；有恢复失败提示时保持停机，用本次完整备份恢复代码。
- 尚未恢复业务时：可用 `node ops/restore-fdm-pricing.cjs "本次.fdm-pricing-backup目录"` 恢复现场代码，桥接和原服务器分别恢复。云端按仓库运维流程回退应用镜像/提交，勿自行改写数据卷。
- 已产生新记录或申请时：先暂停两端，保留最新账本、回执与待处理申请后排查，不仅回滚数据库，也不要直接恢复旧报价逻辑继续接单。
