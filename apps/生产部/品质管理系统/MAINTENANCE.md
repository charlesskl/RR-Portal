# 修复期间暂停操作

修改或部署前，在品质系统运行环境中使用同一个 `DATA_PATH` 开启维护：

```sh
npm run maintenance:on
npm run maintenance:status
```

命令在数据目录创建 `maintenance.lock`。后台逐请求检查并返回 503，
页面每 5 秒检查一次并显示“系统修复中”；已打开的旧页面即使继续提交，也无法写入服务器。
请求读取完正文后也会重新检查，避免维护开启期间仍落入写入流程。
数据、当前页面内容和未同步草稿不会被清理，不会自动重发。

验证完成后关闭维护：

```sh
npm run maintenance:off
```

页面显示“修复已完成”，提示先核对未保存内容，再点击“刷新后继续”。
不会自动刷新并丢弃表单。全程使用独立健康接口 `/api/health`；
维护状态接口 `/api/maintenance` 仅返回状态，不返回业务数据。

已确认系统正常打开后，如果状态检查暂时断线，只显示“连接中断，保存已暂停”小提示，
保留当前页面可查看、可编辑，记录提交及同步继续受保护；状态恢复后自动撤下提示，不刷新页面。
首次打开尚未取得有效状态、明确开启维护时，仍显示全屏保护。
隐藏标签页不轮询，重新回到页面时再检查，避免后台节流引发无效超时。
已发出的检查在页面隐藏时主动取消；这类取消不当作断线，回到页面重新发起检查。
真正失败会在浏览器控制台记录 `[QMS status]`、故障类别、接口路径和耗时，
不记录账号、表单和响应正文，便于区分网络失败、超时、HTTP 错误和无效响应。

本地服务默认使用 Node 的双栈监听，兼容 `localhost` 的 `127.0.0.1` 和 `::1`，
不再只监听 IPv4。可用 `server/listener.test.js` 验证两种地址的状态读取与维护开关一致。

也可设置 `QC_MAINTENANCE=1` 启动；这种方式需清除环境变量并重启才能解除。
正常部署默认关闭维护；维护标记留在数据目录，不随版本或 PR 发布到生产。

线上版本切换使用 `deploy/update-server.sh`，单独发布或重启使用
`devops/scripts/safe-redeploy.sh qc` 或其 `--restart-only` 参数。
两个入口共享主机锁，切换前确认网关已进入品质维护，放行前检查网关转发的
`/qc/api/health` 返回 200 和 `ok: true`。探测失败会保留品质维护标记。
首次安装先让新网关配置生效；旧配置不支持维护期健康探测时，手动入口会在重启前停止。
